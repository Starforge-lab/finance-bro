# Recovery cryptography feasibility (2026-10-09)

**Decision:** `serenity-kit/react-native-libsodium` is the strongest single binding candidate found for Finance Bro’s selected libsodium APIs: it has native JSI implementations for Argon2id and XChaCha20-Poly1305 plus a React Native Web path to libsodium.js WASM. Its API fit is good enough for a bounded integration spike, but **the binding/source-build gate is not cleared**. The published native package extracts prebuilt libsodium binaries, its own source-build script still pins libsodium 1.0.21-stable, and its example targets React Native 0.83 while this app is on Expo SDK 58 / RN 0.88. Do not freeze the backup format or add the runtime dependency until source-built Android and exact SDK58 native compatibility are demonstrated.

Scope update (2026-10-10): encrypted recovery is deferred beyond the Android
SMS-only 2.0 release. This historical research is retained for later work,
not as a prerequisite for automatic SMS ingestion.

This note addresses feasibility for [#42](https://github.com/Starforge-lab/finance-bro/issues/42) against the F-Droid source-build requirement in [#27](https://github.com/Starforge-lab/finance-bro/issues/27). It is research, not an implementation decision to ship the dependency.

## Candidate and API evidence

The app currently uses Expo `~58.0.6`, `expo-sqlite ~58.0.10`, and `react-native 0.88.0-rc.3` ([mobile package manifest](../../apps/mobile/package.json)). Expo’s SDK 58 reference maps SDK 58 to RN 0.88. The candidate README documents Android, iOS, and web; an Expo config plugin; and a New Architecture example, but that example follows RN 0.83 defaults. The candidate declares broad React/RN peer ranges, which is not proof it builds against RN 0.88. The native compatibility edge therefore remains unverified. [Expo SDK 58 reference](https://docs.expo.dev/versions/v58.0.0/) · [candidate README](https://github.com/serenity-kit/react-native-libsodium/blob/v1.7.0/README.md) · [candidate package manifest](https://github.com/serenity-kit/react-native-libsodium/blob/v1.7.0/package.json)

| Runtime | Concrete API path | Evidence and limits |
| --- | --- | --- |
| Android/iOS | `crypto_pwhash(keyLength, password, salt, opsLimit, memLimit, crypto_pwhash_ALG_ARGON2ID13)` and `crypto_aead_xchacha20poly1305_ietf_encrypt/decrypt` | The native TypeScript surface declares the Argon2id constant and JSI functions. The C++ host function calls libsodium `crypto_pwhash()` with the supplied algorithm, salt, ops and memory limits; separate host functions call XChaCha encrypt/decrypt. These calls are synchronous JSI host functions, so KDF latency and UI-thread blocking need measurement on actual native builds/devices. [native TypeScript bindings](https://github.com/serenity-kit/react-native-libsodium/blob/v1.7.0/src/lib.native.ts) · [native JSI implementation](https://github.com/serenity-kit/react-native-libsodium/blob/v1.7.0/cpp/react-native-libsodium.cpp#L1002-L1068) · [XChaCha implementation](https://github.com/serenity-kit/react-native-libsodium/blob/v1.7.0/cpp/react-native-libsodium.cpp#L1143-L1216) |
| Web | `loadSumoVersion()` before awaiting `ready`, then `crypto_pwhash` and XChaCha exports from `libsodium-wrappers-sumo` | The package’s web implementation delegates to libsodium.js wrappers; the standard build omits `crypto_pwhash_*`, while the Sumo build includes them and contains WebAssembly plus a JavaScript fallback. The main wrapper documentation reports Sumo at about 375 KB minified/gzipped including WASM and fallback. [candidate web README section](https://github.com/serenity-kit/react-native-libsodium/tree/v1.7.0#react-native-web) · [libsodium.js standard/Sumo and WASM docs](https://github.com/jedisct1/libsodium.js#standard-vs-sumo-version) |

There is a documentation inconsistency worth resolving in the spike: candidate README import comments label `crypto_pwhash` and its constants “only with loadSumoVersion with react-native-web”, yet native TypeScript and C++ source expose and implement `crypto_pwhash` and `crypto_pwhash_ALG_ARGON2ID13`. This report relies on the native code as evidence of an implementation, not as evidence that an SDK58 build works. Add native and web tests against the exact installed package before relying on this split API.

The native XChaCha adapter also has a narrower runtime contract than its public TypeScript signature: the signature allows `string | Uint8Array | null` additional data and a string ciphertext, but the implementation throws “input type not yet implemented” for non-string additional data and for string ciphertext on decrypt. Use a fixed UTF-8 string for archive AAD and byte-array ciphertext in a shared adapter, or require an upstream correction; test the native and web paths with the same deterministic vector. Without that restriction/fix, the advertised cross-platform API is not equivalent. [native XChaCha adapter](https://github.com/serenity-kit/react-native-libsodium/blob/v1.7.0/src/lib.native.ts)

The official libsodium guidance recommends XChaCha20-Poly1305 where cross-library interoperability is not required; it permits random 192-bit nonces but forbids reuse of a nonce with the same key, authenticates optional additional data, and rejects invalid authentication tags. Store the archive-format/version context as AAD and generate a fresh nonce per archive. Argon2id requires persisting the algorithm and exact ops/memory parameters with the salt so the same key can be derived later. The interactive baseline uses 64 MiB; choose and benchmark parameters as a user-facing recovery contract, not as unversioned constants. [XChaCha construction](https://doc.libsodium.org/secret-key_cryptography/aead/chacha20-poly1305/xchacha20-poly1305_construction) · [libsodium password hashing](https://doc.libsodium.org/password_hashing/default_phf)

### Isolated WASM check

A temporary directory outside the repository installed `libsodium-wrappers-sumo@0.8.4`. A Node smoke test instrumented `WebAssembly.instantiate` and asserted it was called, derived a 32-byte key using Argon2id with the interactive limits and a fictional password, encrypted/decrypted a fictional payload with XChaCha20-Poly1305 and AAD, and asserted a tampered ciphertext was rejected. All assertions passed, with one WASM instantiation observed. No Finance Bro dependency or lockfile was changed. This verifies the standalone wrapper’s Node/WASM path; it does **not** verify Expo Metro bundling, a real browser, the candidate’s package integration, or native code.

### What the published Android package does

The default npm/Gradle path consumes prebuilt libsodium binaries. I inspected exact `react-native-libsodium@1.7.0` from npm and tag `v1.7.0` (Git commit `052cb17825b2b24e7d616a0264ef339b0e3667f3`; npm tarball shasum `5b1520de8395042b7f22a8aec9894b25680679f8`):

- The published package contains a 19.7 MB `libsodium/build.tgz`. `package.json` includes the `libsodium` directory while excluding only the expanded `libsodium/build` directory; `postinstall` unconditionally extracts `build.tgz`. [v1.7.0 package manifest](https://github.com/serenity-kit/react-native-libsodium/blob/v1.7.0/package.json#L10-L42) · [npm v1.7.0 tarball](https://registry.npmjs.org/react-native-libsodium/-/react-native-libsodium-1.7.0.tgz)
- The archive contains compiled Android `lib/libsodium.so` and `.a` files and an iOS XCFramework. Android CMake declares `sodium` as an `IMPORTED` shared library and links the extracted ABI-specific `.so`; there is no libsodium source compilation in that Gradle/CMake path. [v1.7.0 Android CMake](https://github.com/serenity-kit/react-native-libsodium/blob/v1.7.0/android/CMakeLists.txt)
- CocoaPods also extracts the same archive when the XCFramework is absent and vendors that framework. [v1.7.0 podspec](https://github.com/serenity-kit/react-native-libsodium/blob/v1.7.0/react-native-libsodium.podspec)

### What the source script can do

The repository does have an alternate manual source builder. In v1.7.0, `libsodium/build.sh` pins `libsodium-1.0.21-stable.tar.gz`, downloads that source archive over the network, verifies it with the packaged Minisign key/signature, cross-builds four Android ABIs at API 21 (and iOS when run on macOS), then repackages the generated outputs into `build.tgz`. The script is not invoked by the normal Android Gradle path, and it does not currently accept an offline source tree. It can compile Android libsodium from source, but as published it is not an offline/reproducible F-Droid path. [v1.7.0 source builder](https://github.com/serenity-kit/react-native-libsodium/blob/v1.7.0/libsodium/build.sh) · [v1.7.0 Android CMake](https://github.com/serenity-kit/react-native-libsodium/blob/v1.7.0/android/CMakeLists.txt)

### Current libsodium source and bounded experiment

As of 2026-10-09, the official release index lists `libsodium-1.0.22-stable.tar.gz` (2,096,232 bytes; dated 2026-10-07) and its `.minisig` sidecar. The current upstream `stable` ref resolved to commit `a6a93de672b7e2c6c13a02cbbe0e6457fe9306fd`; a release recipe must pin an immutable revision or exact artifact, not the moving `stable` name. Official libsodium guidance says stable updates remain fully compatible with their point-release parent and do not add features or breaking changes. That establishes the maintenance contract within 1.0.22-stable; it does not by itself validate a binding build or prove an automatic upgrade from 1.0.21. A version/date difference is not evidence of a security defect. [official source releases](https://download.libsodium.org/libsodium/releases/) · [current stable source commit](https://github.com/jedisct1/libsodium/tree/a6a93de672b7e2c6c13a02cbbe0e6457fe9306fd) · [libsodium stable versioning](https://github.com/jedisct1/libsodium-doc/blob/master/installation/README.md#versioning)

I downloaded and extracted only the official 1.0.22-stable source archive in a separate temporary directory. The source includes generated `configure` and the four Android scripts the candidate expects (`android-armv7-a`, `android-armv8-a`, `android-x86`, `android-x86_64`); their output directory names match the paths CMake selects. The upstream armv8 script includes 16 KB page alignment. This confirms source/script shape only. The archive sidecar is present and its public key matches the key in v1.7.0 and libsodium’s published key, but I did not verify the signature locally because Minisign is unavailable on this host.

### Minimum F-Droid integration route

F-Droid’s inclusion policy requires binary dependencies to come from source compilation or Debian repositories, subject to its documented exceptions. Its build metadata supports pinned source-library revisions and path substitution; it distinguishes `prebuild` (do not produce binaries) from `build` commands that generate binaries. [F-Droid inclusion policy](https://f-droid.org/docs/Inclusion_Policy/) · [F-Droid build metadata](https://fdroid.gitlab.io/jekyll-fdroid/en/docs/Build_Metadata_Reference/)

The smallest plausible route is to supply libsodium 1.0.22-stable from a pinned source revision/artifact, patch `libsodium/build.sh` to accept that local source input and emit ABI outputs directly, exclude the published `build.tgz`, and patch/replace the unconditional postinstall extraction. Run the Android source build with F-Droid’s NDK before the Gradle/CMake link step; the existing CMake import paths can then point to those same-run generated `.so` files. Because the current CMake target is `IMPORTED`, merely adding source to the app or changing the version string will not trigger compilation. This is recipe/source-builder feasibility, not a passed F-Droid gate.

A clean F-Droid build and binary/dependency scan, plus reproducibility and the full locked runtime license/notices audit, remain required. If this route cannot be maintained, evaluate another binding before freezing the recovery format; do not waive the release gate.
## Restore integration hazards in the current app

- **Native fingerprint key:** [`fingerprint-store.native.ts`](../../apps/mobile/src/imports/fingerprint-store.native.ts) reads a 32-byte HMAC secret from SecureStore and generates/stores a new key when absent. The export/import API is private to the provider today; no method restores archived key material through SecureStore. SQLite stores only the public key ID in [`import_key_state`](../../apps/mobile/src/db/schema.ts). [`requiresDuplicateReview`](../../apps/mobile/src/imports/key-state.ts) compares this marker with the active key ID, so replacement keys are detected at the paste flow, but silent key creation itself does not meet #42’s “no silent key regeneration” criterion. Recovery needs an explicit missing/restored-key state and a guarded key-write path.
- **Web fingerprint key:** [`fingerprint-store.web.ts`](../../apps/mobile/src/imports/fingerprint-store.web.ts) stores a nonextractable WebCrypto HMAC `CryptoKey` in IndexedDB and creates one if missing. Preserve same-origin key reuse. Do not serialize/export this CryptoKey into the backup; a fresh origin necessarily gets a different key and needs a recorded key epoch plus duplicate-review gate while retaining restored transaction IDs and tombstones. The current `import_key_state` schema only has one `key_id`, not an epoch or restore state.
- **Ledger replacement:** [`db/index.ts`](../../apps/mobile/src/db/index.ts) memoizes one `DataLayer` over an open `finance-bro.db` connection. The low-level client type in [`db/ledger.ts`](../../apps/mobile/src/db/ledger.ts) exposes `withTransactionAsync`, not an exclusive transaction or database-swap operation; migrations use the nonexclusive method. Expo SDK 58 documents `withExclusiveTransactionAsync` only for native platforms, and says it is not supported on web; `withTransactionAsync` is nonexclusive and can be interrupted by other async queries. Expo also supports WAL, so replacing/renaming a database file while its connection remains live is a hazard by inference, not a tested failure. Stage and fully validate a restore in a separate database, then replace records through a coordinated transaction on the existing connection, gating concurrent app writes across the operation. Native can use its exclusive transaction API if all transaction queries use the provided `txn`; web needs an app-level serialized write gate or another tested atomic approach. [Expo SQLite SDK 58 transaction and import docs](https://docs.expo.dev/versions/v58.0.0/sdk/sqlite/)
- **Imported state:** [`db/schema.ts`](../../apps/mobile/src/db/schema.ts) contains accounts, categories, budgets, bills, transactions and `import_key_state`; there is no preferences table yet. Transactions carry parser provenance, `userEdited`, `deletedAt` tombstones, foreign-key relationships and positive safe-integer-paise constraints. [ledger contract](../ledger.md). Restore validation must include all of these fields/relationships and preserve deleted rows; do not treat a visible-row export as a full backup. The exact backup entity set still needs reconciling with #42 as preferences and any future import-provider metadata are added.

## Gate sequence before implementation or format freeze

1. Pin an exact `react-native-libsodium` source revision and resolve the stale README/API discrepancy. Build its example or a minimal Expo SDK58 app with this repository’s RN 0.88 / New Architecture; exercise Argon2id and XChaCha on Android and iOS. Compare deterministic test vectors across native and web, then measure KDF latency/memory and ensure the user-triggered KDF does not freeze the UI. A build alone is not runtime/device verification.
2. Confirm Metro emits and serves the Sumo WASM asset in the production web export, initializes `loadSumoVersion()` before use, and passes browser tests under the app’s COOP/COEP headers. Expo documents WASM and cross-origin-isolation setup, and this app already configures those headers in [`app.config.ts`](../../apps/mobile/app.config.ts); integration remains untested. [Expo SQLite SDK 58 web requirements](https://docs.expo.dev/versions/v58.0.0/sdk/sqlite/#web-setup)
3. Make an F-Droid build use pinned libsodium 1.0.22-stable source with signature verification and no bundled `.so`/XCFramework input; run the clean F-Droid recipe and its dependency/license/reproducibility checks. Keep the npm/web wrappers’ ISC notices and the native module’s MIT notice.
4. Only after those gates pass, define the archive envelope and then implement the #42 temporary-database validation, atomic apply, native key restore, same-origin/fresh-origin semantics, wrong-password/tamper/truncation/interruption/newer-schema tests, and user-facing password/destination warnings.
