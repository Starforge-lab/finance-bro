# Finance Bro 2.0 platform feasibility

Scope update (2026-10-10): 2.0 now includes Android SMS imports only. This
historical research retains the broader proposal for later work; its iOS,
Gmail, OCR, recovery and widget recommendations are not 2.0 release gates.
Follow [the current roadmap](../v2-roadmap.md) for delivery scope and order.

Researched 9 October 2026. This note recommends implementation paths and records platform limits that must shape the v2 roadmap. It uses current platform documentation and the existing product contract: local-only finance data, deterministic parsing, no durable raw message/receipt content, and no hosted financial AI ([PRODUCT.md](../../PRODUCT.md), [CLAUDE.md](../../CLAUDE.md)). Documentation establishes API behavior; device spikes below are still required before claiming delivery.

Product priorities also reflect the [personal-finance benchmark](https://github.com/Starforge-lab/finance-bro/blob/docs/finance-benchmarks/docs/research/2026-10-07-personal-finance-benchmarks.md): treat documented competitor behavior as reference, not proof that a feature causes retention; preserve corrections and make full backup/restore a first-class reliability feature.

## Decisions

| Capability | Recommended path | Release gate |
| --- | --- | --- |
| Android message imports | Native `SMS_RECEIVED_ACTION` receiver, multipart decode with Android's helper, then pass text only in memory to the shared deterministic parser. On every app open, use the SMS provider for consented catch-up since the last processed provider row. Persist accepted parsed fields and a privacy-safe dedupe token, never the body. | Prove cold-process delivery, parser/SQLite access, install-time SMS permission, and recovery on the supported F-Droid install path. If the background JS runtime cannot safely process a receipt, fall back to on-open catch-up; do not queue message text to disk. |
| iOS message imports | Rohan-owned, user-configured Shortcuts Message automation that passes its input to an App Intent; the intent calls the same local parser/import service. Do not attempt inbox access. | Real-device proof that a trigger with no sender/content filter supplies message text to the intent, runs automatically, and persists through the existing local store. Apple documents the pieces, but not this end-to-end contract. |
| Notification listener | Do not ship as an SMS fallback. | None; it is broader, less complete, and more user-sensitive than SMS permission. |
| Receipt OCR | User-selected image; Android Tesseract with a bundled, audited language model; iOS Vision. Shared deterministic receipt candidate extraction and a review-before-save screen. | F-Droid source-build/license audit and an anonymized receipt corpus with measured amount/date/merchant errors. Never silently accept an OCR total. |
| Email import | Opt-in, user-initiated Gmail OAuth using a native public client, authorization code + PKCE, `gmail.readonly`, direct Gmail API calls, local parsing, and OS-secured refresh token. | Google restricted-scope verification and token lifecycle/disconnect flow; confirm current assessment requirements with Google before public release. No server or Gmail push backend. |
| Product foundations | Encrypted full backup/restore → merchant rules → reconciliation → explicit-input cash-flow forecast → private summary widgets and quick-add App Intents. | Forecasts are estimates until account coverage and starting balances are known; test backup restore before calling it a backup. |

## Automatic message reading

### Android

Android exposes `SMS_RECEIVED_ACTION`; the intent contains the PDUs and `Telephony.Sms.Intents.getMessagesFromIntent()` returns decoded message parts. Use this framework helper for multipart SMS rather than implementing PDU assembly. `RECEIVE_SMS` is needed for arrivals; `READ_SMS` is needed for provider catch-up. Both are dangerous, hard-restricted permissions, meaning the installer must allowlist them before the app can hold them ([SMS intent API](https://developer.android.com/reference/android/provider/Telephony.Sms.Intents), [permission reference](https://developer.android.com/reference/android/Manifest.permission), [SMS provider API](https://developer.android.com/reference/android/provider/Telephony.Sms)).

The receiver should do only bounded work. Android invokes `onReceive` on the main thread; `goAsync()` is still time-limited, and longer jobs belong in a scheduler ([broadcast guidance](https://developer.android.com/develop/background-work/background-tasks/broadcasts)). Recommended flow: request both permissions with a clear opt-in explanation; receive and reassemble the SMS in memory; run the shared parser; save only a candidate's structured fields plus its dedupe identity and minimal provenance; then discard the body and temporary buffers. A normalized institution sender identifier is permitted in planned `sms_refs` provenance, consistently with CLAUDE.md; it is not retained for discarded non-financial messages. A financial-looking unmatched Android message retains only its inbox reference/minimal metadata for on-demand re-read; unavailable originals require manual/paste recovery. Non-financial messages are discarded. Keep logs free of message fields.

The specific Expo/RN headless-runtime path is not established by Android's API docs. Spike it against the actual v2 SDK/new architecture while the app is cold, with multipart, process death, duplicate broadcasts, and DB migration cases. If it cannot finish safely in the receiver window, show imports on next open via provider catch-up. WorkManager is appropriate for durable, deferrable catch-up/retry work, but its execution is system scheduled and is not a promise of instant processing; never put the body in `WorkRequest` input because that persists the payload ([WorkManager guidance](https://developer.android.com/develop/background-work/background-tasks/persistent)). Use provider row IDs for catch-up identity where available and a keyed, versioned local fingerprint only where the live broadcast lacks that ID; include key loss/reinstall behavior in the dedupe test. Do not backfill old messages silently: start from opt-in and make any historical import an explicit, bounded user action.

Do not make the receiver direct-boot-aware. Before first unlock, credential-encrypted app storage is unavailable; finance import has no need to inspect messages while the device is locked. Catch up after unlock/open, and test this behavior on a physical device ([Direct Boot](https://developer.android.com/privacy-and-security/direct-boot)).

F-Droid is the target distribution, but permission availability needs a release spike: hard-restricted SMS permission depends on the installer allowlist, and a sideloaded build is not proof that the F-Droid client grants it. Test install, grant, revoke, and upgrade using the official F-Droid client on supported Android versions and a release APK. Separately, F-Droid requires a free-software app and dependency graph and builds from source; an Apache-2.0 app license alone is insufficient ([Inclusion Policy](https://f-droid.org/en/docs/Inclusion_Policy/), [PackageInstaller allowlist API](https://developer.android.com/reference/android/content/pm/PackageInstaller.SessionParams)). If a Play flavor is later requested, re-check and declare the exact use under Google's current SMS policy; its listed SMS-based money-management exception is reviewed, not an approval guarantee ([Google Play SMS and Call Log policy](https://support.google.com/googleplay/android-developer/answer/10208820?hl=en)).

### iOS

iOS provides no general API for an app to read the Messages inbox. The only plausible automatic import path is a user-created Shortcuts automation: Apple documents a Message trigger with Sender and Message Contains filters, and says communication automations can run without asking when the user enables automatic running ([Message automation triggers](https://support.apple.com/en-ie/guide/shortcuts/apdd711f9dff/ios), [automation running behavior](https://support.apple.com/en-euro/guide/shortcuts/-apd602971e63/ios)). App Intents support `String` parameters, so an intent can accept text if Shortcuts exposes it ([App Intent parameters](https://developer.apple.com/documentation/appintents/adding-parameters-to-an-app-intent)).

**Critical unknown:** these documents do not promise that the received body is available as a Shortcut input, that leaving filters empty means every sender/message, or that this automation fires for all bank messages under lock-screen, Focus, unknown-sender, and iMessage conditions. Do not describe this as universal “automatic reading” until Rohan proves it on a current physical iPhone. The spike should configure no filters and automatic running; send fictional test messages from known/unknown senders; inspect the actual Shortcut Input; invoke the App Intent with that string while the app is closed and locked; verify a parsed candidate reaches the existing database exactly once; and inspect disk/logs for absence of body text. Provide illustrated setup plus paste/share fallback. Apps cannot silently create personal automations.

Apple's SMS filtering extension is not a substitute: it handles only messages from unknown senders and is a filtering extension rather than inbox access; it cannot cover arbitrary existing conversations ([SMS and MMS filtering limits](https://developer.apple.com/documentation/identitylookup/sms-and-mms-message-filtering)). Keep the App Intent adapter in Rohan's iOS ownership. The code path that runs the TypeScript parser and writes the current Expo SQLite database from the intent remains an implementation spike, not a confirmed capability; do not fork parser rules between Swift and TypeScript to make the demo appear complete.

### Why notification access is not the fallback

`NotificationListenerService` receives callbacks for posted/removed notifications after the user grants special notification access. It sees only what apps choose to put in notifications, can miss messages when previews are hidden/disabled, and has no SMS-provider catch-up semantics ([NotificationListenerService API](https://developer.android.com/reference/android/service/notification/NotificationListenerService), [listener settings action](https://developer.android.com/reference/android/provider/Settings)). It also grants visibility across apps' notifications. That is an overbroad permission for this app and makes ingestion less complete than the direct, read-only SMS provider path. Exclude it from v2.

## Receipt OCR and connected email

For receipts, use system image selection rather than broad photo-library access. On Android, the Photo Picker provides a permissionless user-selected media flow ([Photo Picker](https://developer.android.com/training/data-storage/shared/photopicker)). Run OCR locally: Apple Vision explicitly supports offline recognition with processing on device ([Vision text recognition](https://developer.apple.com/documentation/vision/recognizing-text-in-images)); Tesseract is Apache-2.0 with installable language data ([Tesseract installation and license](https://tesseract-ocr.github.io/tessdoc/Installation.html), [language models](https://github.com/tesseract-ocr/tessdata_best)). This pairing avoids making Play Services a requirement on F-Droid. Audit the selected model license and source build separately. ML Kit's bundled text-recognition model can work offline, but its bundled/unbundled paths do not by themselves establish F-Droid license/build eligibility; keep it out of the default stack until that audit passes ([ML Kit model paths](https://developers.google.com/ml-kit/tips/installation-paths)).

OCR produces candidates, not facts. Ask the user to confirm total, date, merchant, and currency; preserve corrected values; discard the source image and recognized text after the import session. Gate launch on a labeled, anonymized set of Indian paper and digital receipts, including English and Devanagari, with false-total and missed-total rates reported. Begin with the most common installed model languages rather than claiming reliable Hindi/UPI coverage before measurement. If uncertain, leave the transaction unsaved and let the user edit or enter it manually.

For Gmail, `gmail.readonly` is the narrowest practical scope that provides message bodies, but Google classifies it as **restricted** ([Gmail scopes](https://developers.google.com/workspace/gmail/api/auth/scopes)). Use a native public-client OAuth flow with PKCE; do not embed a client secret ([Google native-app OAuth](https://developers.google.com/identity/protocols/oauth2/native-app)). Keep OAuth optional and user initiated; query only selected bank senders/date ranges, parse on-device, persist normalized transaction fields and dedupe metadata, and discard MIME/body/attachment data. Store refresh credentials only in OS-secured storage and offer disconnect that revokes/removes them. Google requires verification for public apps using restricted scopes; a server-side security assessment rule depends on how restricted-scope data is stored/transmitted, so ask Google to confirm the exact local-only app's obligations rather than promising an exemption ([OAuth verification](https://support.google.com/cloud/answer/13463073), [verification requirements](https://support.google.com/cloud/answer/13464321)). No backend, Gmail push subscription, or cloud financial AI is compatible with this product boundary.

## High-value local features for the roadmap

1. **Local merchant rules.** Let people map normalized merchant/VPA aliases to a category and show the selected category. Apply only to future, unedited imports; show the matched rule and make edits/reversal easy. Keep rule matching deterministic and store rules in the same local database. Promote corrections into future suggestions only with explicit user action; no model training or remote lookup.
2. **Reconciliation before forecasting.** Add opening balances and cleared/reconciled status per account, then compare the user's statement closing balance to cleared ledger items and show the discrepancy. This is a proven, understandable ledger mechanism; Actual Budget documents the match-to-zero and lock-after-reconcile flow ([Actual reconciliation](https://actualbudget.org/docs/accounts/reconciliation/)). Reconciliation must not overwrite user edits.
3. **Deterministic forecast with visible assumptions.** Project future cash flow from confirmed opening balances, recurring income, due bills, and known scheduled transactions. Show which accounts and obligations are included, missing coverage, and an estimate range; call it a projection, never “available balance.” Do not emit a forecast when a starting balance or account coverage is missing. No generative AI.
4. **Encrypted full backup/restore.** Prioritize this before advanced insights. Export all local ledger entities, categories, rules, schedules, reconciliation state, corrections, tombstones, and dedupe metadata to a versioned, user-selected archive. Exclude raw message/email/receipt content and OAuth tokens. Native HMAC key material is included only inside the encrypted archive; existing nonextractable WebCrypto keys stay nonextractable, with an explicit changed-key epoch and duplicate-review policy on fresh-origin restore. Use a maintained source-buildable crypto library (selected: libsodium Argon2id + XChaCha20-Poly1305, subject to binding/source-build compatibility), never custom crypto; validate the exact Expo/web/iOS/Android/F-Droid build before fixing the format ([Argon2 password hashing](https://doc.libsodium.org/password_hashing), [XChaCha20-Poly1305](https://doc.libsodium.org/secret-key_cryptography/aead/chacha20-poly1305/xchacha20-poly1305_construction)). Restore into a temporary database, validate schema/integrity, then offer explicit atomic replacement. Test wrong password, tampering, interrupted export/restore, app upgrade, and lost password. CSV export remains useful but is not a full backup ([Actual backup scope reference](https://actualbudget.org/docs/backup-restore/backup/)).
5. **Private at-a-glance widgets and App Intents.** Start with month spend and budget remaining only; omit merchant/account/transaction detail by default. Offer a hide-amount setting and iOS lock-screen redaction via `privacySensitive`. Apple widgets share data through an app group and receive scheduled timeline refreshes, not guaranteed real-time refresh ([WidgetKit strategy](https://developer.apple.com/documentation/widgetkit/Developing-a-WidgetKit-strategy), [privacy-sensitive widget content](https://developer.apple.com/documentation/widgetkit/Creating-a-Widget-Extension)). Android periodic widget updates cannot be configured below 30 minutes; update explicitly after an app write and accept system throttling ([Android widget updates](https://developer.android.com/develop/ui/views/appwidgets/advanced)). Add one iOS quick-add App Intent after proving the local DB is safe to share with the intent target. Rohan owns iOS widget/App Intent work.

Before freezing the backup format, validate the selected key-recovery contract: include native HMAC key material only inside the authenticated encrypted archive and reinstall it in protected storage to preserve dedupe. Existing nonextractable WebCrypto keys remain nonextractable; fresh-origin restore uses a declared changed-key epoch and duplicate review, while same-origin key reuse requires validation. Missing keys force duplicate review rather than silent regeneration. Never export key material in cleartext.

## Spike and ship gates

- **G0 — privacy/data contract (Suvo + Rohan):** document transient body handling, candidate schema, dedupe/key-loss behavior, consent and delete semantics; fixture tests prove raw SMS/email/receipt bodies do not enter DB, logs, backups, or telemetry.
- **G1 — Android SMS (#16, Suvo):** actual SDK/native cold-start spike; multipart and duplicate cases; permissions from F-Droid client and direct APK; process kill/reboot/OEM battery restrictions; provider catch-up after lock/unlock. No roadmap promise until live import and catch-up both work or the product text clearly states the fallback.
- **G2 — iOS Shortcuts (#17, Rohan):** verify empty filters, message-body input, automatic run, app closed/locked, and SQLite/parser execution on a physical device. If any-message/input semantics fail, retain manual paste/share; do not invent a private inbox API.
- **G3 — F-Droid build (Suvo):** clean reproducible source build, dependency/license review including OCR and crypto, SMS install grant, no Play Services dependency, no unnecessary network permission outside explicit Gmail, and inspect release artifact for secrets/telemetry.
- **G4 — imports and corrections (Suvo):** fictional/anonymized fixtures across SMS/email/receipt, duplicate/reversal/pending/refund cases, safe integer paise validation, user correction precedence, and a recovery path for unmatched messages.
- **G5 — durability (Suvo):** restore tests on Android/iOS/web before forecast/widget launch; prove cross-version migrations and account-coverage warnings.

The Android SMS feasibility spike is tracked by issue #16 and the iOS Shortcuts spike by issue #17; reuse those before opening implementation issues. Rohan owns iOS platform work. Keep shared parser, data/privacy contract, Android/F-Droid delivery, and cross-platform integration under Suvo's ownership, with review from Rohan where a shared contract changes.
